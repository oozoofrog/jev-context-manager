# JCM 기록 수집·작업 재개 개선 계획

상태: 구현 및 검증 진행. 실제 결과는 capture-recovery-validation.md와 릴리스 기록을 따른다.

## 목표와 확인된 근거

사용자는 평소처럼 작업하고, JCM은 선택한 범위의 기록을 자동으로 보존·판단·회수한다. 스킬 호출 시 현재 상태와 이어갈 일을 설명하며, 목록 표시와 실제 작업 재개의 성공 조건을 일치시킨다.

RunnersHeart의 실제 Desktop 세션에서 다음을 확인했다.

- dev.10 직접 스킬 호출은 실제 Jev 호출 1회에 성공하고 작업 후보 12개를 반환했다.
- 과거 read_thread 이벤트 1,271,165바이트에서 수집이 중단됐다. 새 훅 이벤트가 저장되는 동안에도 과거 이력의 미수집 구간은 남는다.
- entry.tasks는 bootstrap.existing의 blocked 결과를 확인하지 않는다. 목록 응답은 quality=normal, gaps=[]이지만 select_task는 같은 수집 실패에서 중단된다.
- 채팅 간 전달 지시는 FunctionCallOutput이며 현재 파서는 지원하지 않는다. 일반 사용자 직접 입력과 검증 결과를 분리해야 한다.
- 이전 조회에서는 JCM 조회 결과와 중첩된 도구 출력이 이력에 재포함됐다. 원문 보존과 반복 전달 방지를 함께 다뤄야 한다.

## 1. 수집·판단·회수 상태를 일관되게 전달 — P1

목록 경로가 수집 실패를 무시하는 문제부터 수정한다. bootstrap, 작업 목록, 작업 선택, 일반 복원, 상태 조회가 같은 수집 상태를 사용한다.

- 신규 이벤트 수신, 등록 원문 따라잡기, Jev 판단, 현재 요청 연결, 팩 읽기 상태를 별도로 반환한다.
- source별 처리 위치, 마지막 정상 시각, 미수집량, 차단 이유를 제공한다. 과거에 남긴 오류와 현재 해소되지 않은 오류를 구분한다.
- quality=normal은 Jev 판단 결과로 유지하되, 전체 준비 상태를 대신하지 않게 한다.
- 불완전한 기록으로 목록을 보여줄 수는 있지만, 일부 이력 기준이라는 설명과 실제 선택 가능 여부를 함께 반환한다.
- 따라잡기 시도 후에도 막혔다면 선택 단계에서 원인과 복구 행동을 반환한다. 원인을 CURRENT_SELECTION_NOT_CAPTURED 하나로 숨기지 않는다.
- 사용자 안내는 “새 기록 수신 중 / 이전 기록 일부 미반영 / 이어가기 준비 필요”처럼 실제 상태를 설명한다. 영구적인 limited 문구나 이벤트 개수만으로 정상 여부를 판단하지 않는다.

완료 기준: 실제 차단 사례에서 목록·선택·status가 같은 원인을 나타내며, 사용할 수 없는 이어가기를 정상 준비 완료로 안내하지 않는다.

## 2. 큰 이벤트를 보존하면서 수집 진행 — P1

Store.capture의 1MB 실패 경로와 adapter의 행 읽기 제한을 함께 설계한다. 상한 숫자만 높이거나 문제 행을 건너뛰지 않는다.

- 정규화·민감 정보 처리 후의 허용 원문을 분할 blob과 원문 manifest로 보존한다. 단일 논리 이벤트의 식별자, 순서, 해시, 출처를 유지한다.
- text와 public_item에 같은 도구 결과를 중복 직렬화하는 구조를 줄인다. 필요한 원본 메타데이터와 회수용 텍스트 표현을 연결한다.
- 큰 행은 메모리 사용을 제한하는 읽기·임시 저장 경로로 처리한다. 디스크 부족·손상 등 실제 자원 오류는 명확하게 보고한다.
- 저장 완료 전에는 커서를 전진시키지 않는다. 중단·재실행 시 이미 저장한 조각을 재사용하고 이벤트를 중복 생성하지 않는다.
- 삭제·tombstone·범위 제한·무결성 검사·동시 수집에도 분할 자료의 정책을 적용한다.
- 복구한 원문에 Jev가 기존 분할 판단 경로로 참여하게 한다. 로컬 저장 성공과 Jev 처리 완료를 구분한다.
- 기존 기록과 범위를 보존한 채 멈춘 위치에서 재개하고, 후속 사용자 결정까지 따라잡는다.

완료 기준: 이번 1.27MB 구조 및 현재 행 제한을 넘는 합성 사례에서 원문 재구성·중단 복구·중복 방지·후속 이벤트 수집을 확인한다. 실제 세션에서도 수집 시점에 확정한 관측 범위까지 커서가 진행하고 남은 공백을 정직하게 보고한다.

## 3. 현재 요청의 정확한 연결과 채팅 간 전달 지원 — P2

- 직접 사용자 입력과 신뢰할 수 있는 호스트 전달 지시를 구분하는 요청 식별 계층을 만든다.
- 호스트가 제공하는 출처, 대상 세션, 턴, 항목 ID로 요청을 고정한다. 도구 출력 문자열의 태그만으로 신뢰하지 않는다.
- 일반 도구 결과나 그 안에 인용된 지시는 실행 권한을 얻지 않는다. 검증할 호스트 정보가 부족하면 unsupported로 반환한다.
- 현재 요청을 찾지 못할 때 이전 마지막 사용자 메시지에 자동 연결하지 않는다.
- bare skill 호출, 범위 선택 응답, 작업 선택 응답, 구체적인 작업 요청에 같은 연결 규칙을 적용한다.

완료 기준: 직접 입력·실제 채팅 간 전달을 각각 검증한다. 다른 턴·다른 프로젝트·가짜 전달 문자열은 거부하고, 새 요청을 과거 dev.6 호출에 연결하지 않는다.

## 4. 반복 조회로 이력이 불어나는 문제 — P2

- JCM이 출력한 파생 자료에 원문 ID와 출처를 붙이고, 회수된 원문이 다시 출력된 경우 그 관계를 저장한다.
- 원본 감사 기록은 보존하면서 같은 원문을 독립된 새 사실로 반복 판단·전달하지 않는다.
- 실행 파일 이름이나 문자열 포함 여부만으로 도구 결과 전체를 제외하지 않는다. 감싼 명령에 새로운 제품 결과가 섞여 있으면 그 부분은 보존한다.
- read_thread 결과처럼 다른 대화를 포함한 자료는 현재 채팅의 직접 사용자 지시와 구분한다.
- status와 작업 목록은 기본 응답을 작게 만든다. 전체 snapshot과 원문은 필요할 때 참조·페이지로 읽는다.

완료 기준: 같은 작업의 복원을 반복해도 원문 복사본이 재귀적으로 늘어나지 않으며, 이후 추가된 결정·수정·검증 결과는 회수된다. 임의의 후보 수·호출 수 제한으로 해결하지 않는다.

## 5. 사용자 동작과 명령 설계

### 기본 판단

지속적인 특별 모드는 추가하지 않는다. 사용자는 현재 모드를 기억할 필요 없이 자연어로 작업한다. 수집 중·따라잡는 중·일부 누락·중지는 사용자가 전환하는 모드가 아니라 관측된 상태다.

현재 내부 CLI에는 status, doctor, entry, disable, forget 등이 이미 있다. 부족한 것은 명령의 개수보다 상태 설명과 안전한 따라잡기 동작이다. 새 slash command나 여러 스킬을 늘리지 않고 astra-continuity 하나의 동작으로 정리한다.

| 사용자 표현 | 의도와 동작 |
|---|---|
| 스킬만 호출 | 신규 프로젝트는 상황·관리 범위 선택, 관리 중이면 상태·작업 목록 |
| JCM 상태 확인해줘 | 수신·미수집·판단·회수 상태와 마지막 확인 시점을 조회. 수집·Jev를 시작하지 않음 |
| 빠진 기록 반영해줘 / JCM 기록 업데이트해줘 | 선택된 범위와 등록된 출처만 따라잡고 미처리 판단을 진행. 제품 작업을 시작하거나 관리 범위를 확장하지 않음 |
| 이어갈 작업 보여줘 | 현재 수집 상태를 포함한 작업 목록과 다음 선택 제공 |
| JCM 기록 중지해줘 / 다시 시작해줘 | 기존 비활성·재개 정책을 적용하고 실제 적용 범위를 설명 |
| 특정 세션 기록 삭제해줘 | 정확한 세션을 식별해 기존 forget 적용. 대상이 모호할 때만 확인 |

“업데이트”는 명시적으로 기다려 완료를 확인하는 편의 동작이다. 자동 수집과 일반 요청 복원도 같은 따라잡기 구현을 사용하며, 매 세션마다 사용자가 실행해야 하는 필수 단계로 만들지 않는다. 기록됐다는 말과 Jev 판단·현재 작업에 실제 사용됐다는 말을 구분한다.

### 내부 명령 변경안

- status: 부작용 없는 간결한 현재 상태. 전체 진단은 상세 출력으로 분리.
- doctor: 지금은 status와 같은 결과를 반환하므로, 연결·출처·저장소·요청 지원 여부를 진단하고 조치 방향을 설명하도록 역할을 분리. 진단 자체는 데이터를 수집하거나 Jev에 보내지 않음.
- sync 신설: 기존 범위의 수집 재개와 미처리 판단을 위한 재실행 가능한 단일 진입점. 사용자 자연어 “업데이트”와 자동 경로가 같은 구현을 공유. 관측한 처리 범위와 잔여 작업을 반환하며 영구 대기하지 않음.
- 별도 checkpoint 모드, 수동 요약 필수 단계, 일반 도구 결과를 지시로 승격하는 강제 옵션은 추가하지 않음.

## 6. 검증·배포 순서

1. 기존 회귀 검사를 유지하고 이번 실패 구조를 익명 합성 fixture로 재현한다. 목록 차단 상태 누락과 큰 이벤트 뒤의 수집 정지를 먼저 실패 사례로 고정한다.
2. 1·2단계를 구현하고 저장 무결성, 범위·삭제 정책, 중단 재시도, 실제 세션 따라잡기를 검증한다.
3. 3·4단계와 사용자 동작을 구현한다. 전달 지시의 권한 검증과 파생 자료의 중복 방지를 각각 검증한다.
4. 실제 Desktop 직접 호출 → 작업 선택 → 해당 작업 관련 기록 읽기 → 현재 산출물 대조를 확인한다. 목록 표시만으로 통과시키지 않는다.
5. 실제 전달 지시 경로와 독립된 새 CLI 세션 복원을 별도로 검증한다. 현재 요청, 최신 교정, 완료 여부를 실제 결과에 반영했는지 확인한다.
6. 기존 설정·원문·범위·삭제 이력을 백업·보존하고 기존 릴리스 절차로 배포한다. 설치, 새 세션 로딩, 실제 Jev 호출, Desktop 동작 결과를 각각 보고한다.

실제 사용자 작업의 완료·수정은 별도 지시 범위에 따른다. 검증을 위해 완료된 Blender 작업을 임의로 다시 수행하지 않는다. 새 세션/실제 채팅에 검증 지시를 보내는 단계에서는 해당 실행 범위가 승인돼 있는지 확인한다.

## 변경 대상

store/adapter 및 분할 원문 접근 계층, bootstrap/entry/worklist/coordinator의 상태 계약, 요청 출처 검증, follower 재개, CLI의 status/doctor/sync, 스킬·user-guide, 관련 단위·회귀·실사용 검증 도구.

이 계획은 기존 관리 범위를 자동 확장하거나 기존 원문을 삭제하지 않는다. 계획 작성 시점에는 구현·설치·배포를 수행하지 않았다. 이후 구현과 검증 결과는 별도 검증 보고서에 기록한다.
